01

C/S、P2P 与混合结构：分发公式来自瓶颈

考法：套 Dcs 和 Dp2p 公式，解释为什么 P2P 随 N 增大更可扩展。

定义

应用体系结构描述应用进程如何组织通信；C/S 依赖中心服务器，P2P 中节点既下载也上传，混合结构结合两者。

解释

  • C/S：服务器必须上传 N 份文件，且最慢客户端下载一份文件。
  • P2P：服务器至少上传 1 份文件，最慢 peer 至少下载 1 份文件，系统总上传能力为 us + Σui。
  • P2P 的自扩展性来自 peer 数增加时，总上传能力也增加。

做题步骤

  • C/S: Dcs >= max(NF/us, F/dmin)。
  • P2P: Dp2p >= max(F/us, F/dmin, NF/(us+Σui))。
  • 单位必须统一：Gb/Mb/kb 不统一会直接错 1000 倍。

为什么这样设计

  • 分发时间下界来自“至少要传多少 bit”和“瓶颈速率是多少”。
  • C/S 的服务器上传是集中瓶颈；P2P 把上传压力分摊给所有 peer。

作业/考试例子

作业三 F=15Gb、us=30Mbps、dmin=2Mbps 时，F/us=500s，F/dmin=7500s；N=100,u=1Mbps 时 P2P 第三个下界为 100F/(30Mbps+100Mbps)。

02

DNS 查询：主机递归，本地 DNS 对外迭代

考法：写 H1 获取 www.xyz.com IP 的完整过程，区分根/TLD/权威服务器和缓存。

定义

DNS 是分布式层次数据库和应用层协议，用资源记录把域名映射到 IP、别名、邮件服务器或权威服务器。

解释

  • 主机通常向本地 DNS 发递归查询：希望本地 DNS 直接返回最终答案。
  • 本地 DNS 缓存未命中时，通常对根、TLD、权威 DNS 做迭代查询。
  • 缓存带 TTL，短时间再次访问可跳过完整根/TLD/权威查询路径。

做题步骤

  • 过程题按 8 步写：H1->本地、 本地->根、根返回 TLD、本地->TLD、TLD 返回权威、本地->权威、权威返回 A、本地返回 H1。
  • 不要写根服务器直接返回 www 的 IP；根通常返回 TLD 服务器线索。
  • 如果题目说缓存为空，第一次必须完整查询；再次访问才强调缓存。

为什么这样设计

  • 层次结构避免单点数据库过大，也便于分布式管理域名。
  • 缓存降低延迟和上级 DNS 负载，但 TTL 保证记录变化后最终能更新。

作业/考试例子

作业三中 D1 缓存为空时，D1 先问根得到 .com 的 D2，再问 D2 得到 dns.xyz.com，最后问 dns.xyz.com 得到 www.xyz.com 的 A 记录。

03

DNS 资源记录：A、NS、CNAME、MX 的 name/value 怎么写

考法：注册 xyz.com 时在 .com TLD 和权威 DNS 中分别添加哪些记录。

定义

DNS 资源记录 RR 形式为 (name, value, type, ttl)，type 决定 name 和 value 的语义。

解释

  • A：主机名 -> IPv4 地址。
  • NS：域名 -> 该域权威 DNS 服务器名；通常还要给权威 DNS 服务器名配 A 记录。
  • MX：邮件域 -> 邮件服务器主机名；邮件服务器主机名也需要 A 记录。
  • CNAME：别名 -> 规范主机名。

做题步骤

  • 先判断记录放在哪一级 DNS：TLD 中放委派记录，权威 DNS 中放本域服务记录。
  • Web 服务器通常写 www 的 A 记录。
  • 邮件要两条：域的 MX + 邮件服务器主机名的 A。

为什么这样设计

  • NS 记录解决“谁负责这个域”，A 记录解决“这台服务器在哪里”。
  • MX 不直接写 IP，而是写邮件服务器名，便于更换服务器地址。

作业/考试例子

作业三：.com TLD 中插入 (xyz.com, dns.xyz.com, NS) 和 (dns.xyz.com, 130.20.4.18, A)；xyz.com 权威 DNS 中插入 www 的 A、xyz.com 的 MX、mail.xyz.com 的 A。

常考 RR 类型

Typenamevalue典型用途
A主机名IPv4 地址www.xyz.com -> 130.20.5.10
NS域名权威 DNS 主机名xyz.com -> dns.xyz.com
CNAME别名规范主机名www -> server.example.com
MX邮件域邮件服务器主机名xyz.com -> mail.xyz.com
04

HTTP、Cookie 与 Web 缓存：无状态协议如何维护会话

考法：HTTP 非持久/持久连接、Cookie 四个组成部分、条件 GET 和 304。

定义

HTTP 是基于请求/响应的应用层协议，协议本身无状态；Cookie 和服务器端状态让 Web 应用能识别会话。

解释

  • 非持久 HTTP：每个对象单独 TCP 连接，单对象约 2RTT + 传输时间。
  • 持久 HTTP：复用 TCP 连接，减少重复握手和慢启动开销。
  • Cookie 机制包括响应头 Set-Cookie、请求头 Cookie、客户端保存、服务器数据库。
  • Web 缓存用条件 GET：If-Modified-Since/ETag；未修改可返回 304。

做题步骤

  • 问 HTTP 是否有状态：答协议无状态，但 Cookie 可在其上维护会话。
  • 问访问延迟：先判断是否含 DNS、是否需要 TCP 建连、是否持久连接。
  • 缓存题写清命中直接返回、过期/验证时条件 GET、未修改 304。

为什么这样设计

  • 无状态让服务器协议逻辑简单、易扩展。
  • Cookie 把会话标识放到后续请求里，避免每个请求都重新登录。
  • 缓存减少源服务器负载和接入链路流量。

作业/考试例子

浏览器首次访问收到 Set-Cookie: id=...；之后同站点请求带 Cookie: id=...，服务器据此找到购物车或登录状态。

SMTP 与 MIME：邮件传送状态和二进制附件

考法：SMTP 三阶段、TCP/25、push/pull 区分、MIME 为什么需要。

定义

SMTP 是邮件服务器之间推送邮件的应用层协议；MIME 扩展邮件格式，使非 ASCII 文本和附件可以通过邮件系统传输。

解释

  • SMTP 基于 TCP，服务器熟知端口 25，采用命令/响应交互。
  • 三阶段：连接建立、邮件传送、连接释放。
  • 原始 SMTP 面向 7 位 ASCII；MIME 用 Content-Type、Content-Transfer-Encoding 等头部描述和编码附件。

做题步骤

  • 过程题写：TCP 建连 -> 220/HELO(EHLO) -> MAIL FROM -> RCPT TO -> DATA -> . -> QUIT。
  • 问为什么用 TCP：邮件要求可靠、按序、完整传输。
  • 问附件：写 MIME + Base64 等编码 + 接收端解码恢复。

为什么这样设计

  • SMTP 是 push，因为发送方邮件服务器主动把邮件推到接收方邮件服务器。
  • 用户读取邮件通常是 pull，例如 POP3/IMAP/HTTP。
  • MIME 让原本只适合文本的邮件协议能传图片、文档和多部分内容。

作业/考试例子

作业三 project.doc 附件会作为 MIME part，带 Content-Type: application/msword 和 Content-Transfer-Encoding: base64，经过 SMTP 文本通道传输。

Socket 调用关系：客户端主动 connect，服务器被动 accept

考法：实验/概念题问 TCP 客户端和服务器端 socket 调用顺序。

定义

Socket 是应用进程使用传输层服务的接口；TCP 服务器监听端口并接受连接，客户端主动连接服务器。

解释

  • 服务器：socket -> bind -> listen -> accept -> recv/send -> close。
  • 客户端：socket -> connect -> send/recv -> close。
  • accept 返回的是新的连接 socket；监听 socket 继续留着接收后续连接。

做题步骤

  • bind 绑定本地 IP/端口；listen 把 socket 变成监听状态。
  • connect 触发 TCP 三次握手；accept 在连接建立后返回。
  • 不要用监听 socket 直接和某个客户端收发应用数据。

为什么这样设计

  • 分离监听 socket 和连接 socket，让一个服务器端口能同时服务多个客户端。
  • 客户端主动 connect 与服务器被动 accept 对应 TCP 主动打开/被动打开。

作业/考试例子

HTTP 服务器 bind 到 0.0.0.0:80 并 listen；浏览器 connect 到服务器 IP:80 后，服务器 accept 得到连接 socket 处理该请求。
